# 面试自检 8 题（结合本项目真实数据）

> 每题 ≤5 行，数字必须能在仓库里找到出处。合上笔记能脱稿答出前 5 题。

## 1. 为什么不用 Dify / 现成框架？

先用 Dify 搭过原型，发现三个具体问题：检索过程是黑盒、没有评测手段、工具报错整条链路中断。
所以手写检索和分发循环，代价是多花约一周，收益是每一步能打印 source/distance、能跑 20 条评测、异常能回灌给模型。
第 1–2 周再把循环迁到 LangGraph，是为了补多轮状态和流式，不是把可控性换回去。

## 2. 怎么治理幻觉？

三层：只把检索到的片段给模型；prompt 明确「资料中没有就说资料中没有」；评测集里 5 条 `no_answer` 专测拒答，当前 **5/5**。代价是误拒答，用户得换个问法；我选择宁可拒答也不编。

## 3. 你怎么评估一个 RAG 系统好不好？

20 条自建评测集，10 可答 / 5 应拒答 / 5 跨段；三项指标是检索命中率 **0.90**、拒答正确率 **1.00**、要点覆盖率 **0.80**。人工标 0/1，因为只有 20 条且每条都要能解释。只改 `overlap` 一处，命中率 0.90→0.80，说明这个方向不对，已回退。

## 4. chunk_size 和 overlap 怎么定？

500/50 是起步默认值，没有调参。Day4 把 `overlap` 提到 100 做单变量实验，命中率从 0.90 降到 0.80，归因是同文档相邻片段重叠变多、挤占 top3，已回退。按标题切、表格单独处理还没做，写在已知限制里。

## 5. 工具调用失败、参数错、模型死循环怎么办？

循环最多 3 轮；缺参数抛 `ValueError`，把「缺少 query」回灌给模型；工具异常转成 `TOOL_ERROR` 文本，让模型换策略；超轮返回明确说明并带上最后一次错误。三类失败都用 `FAULT_MODE` 复现过，README 有 4 段对话记录。

## 6. 检索结果不准，你的排查顺序是什么？

先看命中的 `source` 和 `distance`：没命中 → 切片或 embedding 问题；命中但答错 → 上下文顺序或 prompt。两类都用同一套 20 条评测验证，一次只改一处。Day4 的 q04/q05 就是前者，已记成失败案例。

## 7. 多轮对话的状态怎么管？为什么需要状态机？

手写版状态就是 `msgs` 列表，每轮追加 assistant 和 tool 消息；3 轮上限防死循环；超长按 token 预算裁最早轮次。并发隔离和持久化还没做，第 1–2 周用 LangGraph 的 `StateGraph` 与 checkpoint 补。

## 8. 成本和延迟怎么控制？

`smoke_test` 每次打印 token 和耗时，单次调用约 **30 token、7.45 秒**（含网络）。完整 RAG 问答的 token/耗时还没单独埋点，是第 1–2 周补的；计划加缓存、限流、流式降首字延迟。
