# 目标与验收标准

## 1. 把模糊目标改写成可验证目标

| | 原话 | 改写后 |
| --- | --- | --- |
| 岗位 | 大模型应用开发工程师 | 初级 / 1–2 年经验档：Python + LLM API + RAG + Function Calling + 服务化 |
| 期限 | 1–2 个月 | 8 周，第 8 周末验收 |
| 结果 | 能找到工作 | 「拿到 ≥2 场技术面试」为**领先指标**；offer 是滞后指标，不由学习单独决定 |

**为什么用面试数而不是 offer 当验收**：offer 受市场、投递量、面试发挥影响，不是学习计划的因变量。面试邀约数能直接反映「简历 + 作品集是否被市场认可」，可控、可测、可归因。

## 2. 终点硬门槛（第 8 周末，逐条勾）

- [ ] 2 个**公开** GitHub 仓库，各含 README、可运行代码、明确技术栈
- [ ] 每个项目有 1 个**公网可访问**的 Demo 链接（面试官不用装环境就能试）
- [ ] 每个 README 含：架构图、启动命令、环境变量、**评测数据表**、至少 2 个已知失败案例
- [ ] 简历有 2 条项目描述，每条至少 1 个可验证数字（评测集条数、指标提升、QPS、成本）
- [ ] 不看笔记能口述回答 [[面试自检题库]] 的 8 个问题
- [ ] 投出 ≥ 30 份简历，拿到 ≥ 2 场技术面试
- [ ] 有 1 篇技术复盘文章（写「为什么某个优化有效 / 无效」，不是教程转载）

## 3. 第 7 天末的阶段门槛（启动周验收）

- [ ] 1 个公网可访问的项目，能答对至少 1 类真实问题
- [ ] 1 张「改动前 vs 改动后」的评测对比表
- [ ] 1 段工具调用失败但不崩溃的演示记录
- [ ] 2 条写好数字的简历项目描述
- [ ] `python check.py` 全部 PASS（见 [[交付自检脚本]]）
- [ ] 连续 7 天打卡，每天都有 commit 或笔记证据

**阶段门槛没全勾上 → 不要进第 2 周**，按 [[目标反推校验记录]] 的复检规则调整，先把缺口补上。

## 4. 岗位能力对照（2026 年 JD 高频项 → 本库覆盖位置）

| JD 关键词 | 本库对应 | 你的起点差距 |
| --- | --- | --- |
| Python / LLM API 调用 | [[Day1_岗位反推与项目骨架]] | 已会 Python，补 API 工程细节 |
| RAG：切片、Embedding、向量检索、重排、上下文压缩 | [[Day2_手写最小RAG]]、[[Day4_单次可归因优化]] | **最大缺口**：工作流里是黑盒 |
| Function Calling / 工具编排 / 状态流转 | [[Day5_工具调用与异常处理]] | 低代码里配过，没手写分发循环 |

| 异常、超时、降级等生产问题 | [[Day5_工具调用与异常处理]] | JD 明确吐槽「只会复制 Demo」的点 |

| LangGraph / Agent 框架 | [[8周路线图]] 第 1–2 周 | 启动周**故意不碰**，先手写再上框架 |

## 5. 起点判断（直说）

你已会的工作流编排是**业务原型能力**，不是工程能力。2026 年招聘方对「只会配 Dify / 只会跑 Demo」的评价是负面的：缺异常处理、状态流转、生产问题经验。
所以本库的主线只有一句：**把你在工作流里配过的逻辑，用 Python 手写一遍，加上评测数据和失败处理**。
简历上不要写「熟悉 Dify」当核心技能，写「手写 RAG 链路 + 自建评测集 + 工具调用容错」。
